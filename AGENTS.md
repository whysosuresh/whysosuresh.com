# Agent guide: whysosuresh.com

This repository is whysosuresh.com, Suresh's home page: the static folder `site/`, served by one Cloudflare Worker, `whysosuresh-com` (`wrangler.jsonc`), which the `deploy` job in `.github/workflows/site.yaml` deploys on every merge to `main`. The Worker runs code only for `/api/*` and `/threads/*` (`src/`): the note flow's send, which keeps a typed note as a new thread after a bot check and two daily limits, the site's answer to Cloudflare Access's sign-in question for invited people under `/api/access/` (`src/evaluate.ts`), the threads' private calls under `/threads/api/`, behind their Cloudflare Access application, a public thread's calls under `/api/threads/` with no sign-in (`src/public.ts`), and the threads page (`src/pages.ts`), which it hands over from `site/threads/index.html` through the assets binding at `/threads/` and at every thread's own address, because no file can sit at every number. Everything Suresh keeps is a numbered thread with a history, kept by one store (`src/store.ts`). Every other page comes straight from `site/`, and `/inbox`, the threads' old address, redirects to `/threads/` (`site/_redirects`). Everything else it runs on (the zone, its records, the www redirect, the zone's settings, the database, the pages bucket, the bot check and Access) is declared under `infrastructure/` and applied by Planton; read [`infrastructure/AGENTS.md`](infrastructure/AGENTS.md) before touching any of it. These are the laws for any change here.

## Laws

- **Run `npm run check` before every push.** It runs the three strict type checks (the tests and `tools/`, the site's scripts, the Worker, and that `worker-configuration.d.ts` matches `wrangler.jsonc`), wrangler's dry run, the site tests (`test/site.test.ts`, `test/markdown.test.ts`, `test/keys.test.ts`, `test/share.test.ts`), the command line's tests (`test/inbox-cli.test.ts`) and the Worker tests (`test/talk.test.ts`, `test/threads.test.ts`, `test/threads-door.test.ts`, `test/members.test.ts`, `test/public.test.ts`, `test/evaluate.test.ts`, `test/pages.test.ts`, `test/routing.test.ts`, `test/migrations.test.ts`), which run the dry run's bundle in workerd, in front of `site/` with the routing `wrangler.jsonc` declares. Local commands run on the Node in `.nvmrc`. `npm run dev:signed-in` serves the same bundle at `http://localhost:8790/` with made-up threads and Access played as the owner (`test/dev-signed-in.ts`, with one public thread and notes on it; `--signed-out` for a visitor, who sees that thread's public view, `--member <address>` for a person invited to one thread), which is how the threads page is looked at in a browser before a deploy.
- **Code style.** Strict TypeScript with no `any`; the site's scripts are plain JavaScript under `// @ts-check`. `tools/` is TypeScript that Node runs as is, so it uses only syntax Node can strip (no `enum`, `namespace` or parameter properties) and no dependency. Every file opens with a comment that says what it is for. `worker-configuration.d.ts` is generated (`npm run types`), never edited by hand.
- **The Worker has no runtime dependencies.** Everything it needs is in the runtime and its bindings, so the deploy installs nothing but wrangler. It answers only JSON, with `Cache-Control: no-store`, with two exceptions: a page saved into a thread (`src/page.ts`), the stored HTML its frame loads, which is answered with its own sealing CSP and `Cache-Control: private, no-cache` revalidated by its ETag; and the threads page at a public thread's address (`src/pages.ts`), the site's own shell with that thread's title and link-preview tags written in by `HTMLRewriter` (as text or escaped attributes, never markup), fetched without the browser's conditional headers and answered without an ETag, so no browser keeps a stale title. Every other address gets the shell byte for byte.
- **Nothing personal in a log line:** no name, email, address or token. A refusal logs its status and reason only. Cloudflare's automatic request records stay off (`invocation_logs: false` in `wrangler.jsonc`), because nothing says they leave out the visitor's address. No table keeps a visitor's network address either; the limits count a salted hash that lives one day. The only email addresses kept are a visitor's who typed one for a reply (a site note's sender's in `threads`, and a note's on a public thread in `comments`) and the people Suresh invites (`people`), which their sign-in needs; a visitor's never reaches anyone but the owner and the sync.
- **Migrations are numbered and applied before the code.** `migrations/NNNN_name.sql`; the deploy applies them, then deploys. A migration adds, or drops only what no deployed code reads, in a deploy after the one that stopped reading it, so a failed deploy leaves a working site. It never renames. A new column arrives in the migration beside the code that first writes it.
- **The private door admits three callers: the owner's email, the sync's service token, and the email of a person invited to a thread, checked by the Worker on every request.** Access guards `/threads/api` at the edge, one application with three policies (the owner's address, the sync's token, then an external evaluation the site itself answers), and `src/access.ts` checks Access's signature, issuer, audience and times again on every call under `/threads/api/`, against that application's tag (`THREADS_ACCESS_AUD`), so a token signed for any other application never opens it, then names the owner's address (`INBOX_OWNER_EMAIL`), the sync's client id (`INBOX_SYNC_CLIENT_ID`) or any other address as a candidate, whom `src/threads.ts` admits only while that address has an invitation that stands (`isInvited` in `src/store.ts`); anyone else is refused with 403 `caller`. Access never guards a thread's own page, only its calls. A new caller is a new Access policy and a new check here, in one PR. The owner's page reads, starts threads of his own, makes the moves, comments and rewrites a thread's title, living summary or main text, every write only from his own page (`src/request.ts`). The sync reads, adds items (each once, by the origin it names), makes the page's moves, comments and rewrites a thread's title, living summary or the main text of a thread it wrote, without the page's same-origin check, which guards only a signed-in browser; marking the owner's mail opened stays his, and filing an item as an issue is the sync's alone. A visitor's own words are never rewritten. Nothing it adds or moves happens without the owner's word in the sync; that rule is the sync's, and the Worker's part is to refuse what isn't one of these. Inviting a person to a thread, and taking it back, is the owner's alone, from his own page: the sync never invites anyone, because an invitation grants access. For the same reason, making a thread public and taking it back (`publish`, `unpublish`), and showing, dropping or holding a visitor's note on it, are his alone, and the sync never writes a comment for anyone (`audience` `public`), so nothing it transcribes is published without him.
- **An invitation opens exactly one thread.** An invited person reads the threads they are in, their pages, and comments on them, and nothing else: every read and their one write take the caller as the store's reader (`readable` in `src/store.ts`), so a thread they aren't in is a row the query can't see and answers exactly as a number never used, and every other call is refused with 403 `owner-only` before anything is read. What they see is shaped in `src/threads.ts`: never a visitor's email, an origin, an issue link, a drop reason, the owner's mail opening or an earlier version of any text, never a comment for the owner alone (`audience` `owner`, "Only me"), and the people by name only. A test per route holds each of these (`test/members.test.ts`). The threads page is one app that knows its caller (`GET /threads/api/me`): an invited person gets their threads and a comment box, and none of the owner's controls, which the Worker would refuse anyway. The owner invites from his own page (Share, `site/app/share.js` holding its words and the draft), and the invitation is a draft his own Gmail opens: no mail is ever sent from the site.
- **A public thread is his own, and strangers read only what he chose.** Only a thread of his own (`source` `self`) may be public: a site note's and a told thread's words are someone else's. Every public query holds that condition in its own SQL (`PUBLIC` in `src/store.ts`), and every number that isn't a public thread answers the same 404 bytes on each public call (`src/public.ts`). A stranger reads the thread's title, summary, space, its main section as it now stands (a page's versions only while the page is its main section, never their claude.ai source) and the comments written as Public that are shown, by name: never its status, origin, sender, people, history, ids or last activity. A comment written before the thread went public keeps its audience. A visitor's note on a public thread runs every visitor note's checks (`src/note.ts`, shared with the note flow, and its one daily budget) and is kept as a comment that waits for his OK (`state` `pending`); it is shown only once he OKs it, its words are always drawn as typed, never as Markdown, and invited people never read a waiting or dropped note or the events that would tell them of one. Public threads are kept out of search results (`noindex` on the page, `X-Robots-Tag` on the calls), but anyone who tries a number reads a public thread: public means readable by anyone, not unlisted. A test per route holds each of these (`test/public.test.ts`).
- **Access's sign-in question has one answer, the store's.** The members' Access policy asks `POST /api/access/evaluate` at sign-in, and the site answers yes exactly when `isInvited` holds, the same question the door asks on every call, so the edge and the Worker can't disagree about who is invited. The answer is signed with the Worker secret `THREADS_EVALUATION_KEY`, whose public half the Worker derives and serves at `/api/access/keys`; without it both answer 503, which Access counts as no (`src/evaluate.ts`).
- **The owner's email address is in no file.** The repository is public. Access reads it from a Planton secret, the Worker from the GitHub environment `production`, and the threads page from his sign-in; the site test fails on any address in the repository's files.
- **The "Send a note" doors open the note flow.** The home page and the Talk to me page each carry one (`data-talk`, first among their doors), and `/#talk` and `/#talk/<topic>` open it too; the test holds both. The doors arrived only once the inbox (now the threads) was live and proven, so nobody writes into a box no one reads: a change that takes the threads away takes the doors with it.
- **One topic list.** `site/talk-topics.js` is the topics a note can be about, read by the page and imported by the Worker. It stays plain data and pure functions, with no page and no side effect; the Worker's type check (no browser library) and the site test hold that. `site/spaces.js`, what a thread can be about, follows the same rules and holds every topic; the site test holds that too. So does `site/app/markdown.js`, the threads' Markdown reader, which the Worker imports for a public thread's link preview, so Markdown is read one way on the site.
- **`site/` is an allowlist.** Every file it holds is served, and the list in `test/site.test.ts` names each one. A new file is added there on purpose, never by accident.
- **Links are clean and root-absolute:** `/` and `/feedback`, never `feedback.html` or `index.html`. The Worker redirects those with a 307, and a relative link breaks on the 404 page, which is served at any path.
- **Never `no-referrer`,** on a page, an element or a header. The YouTube player refuses to play without a referrer.
- **A page saved into a thread runs sealed, never on the site's own terms.** It is a Claude artifact's own HTML, so it is served only at its thread's call address with the headers `src/page.ts` sets (a CSP `sandbox` without `allow-same-origin`, claude.ai's page contract as its sources and no wider, `connect-src 'none'`), and framed by the threads page with the same sandbox tokens. The site's own CSP gains only `frame-src 'self'` for it; every library and font host lives in the frame's CSP alone. A page is saved by the sync only, as a new version: the object in the private bucket first, then its row, the object deleted again when the row isn't kept; versions are never overwritten or deleted.
- **`site/_headers` matches the pages.** The test holds the expected set. A new kind of resource changes the CSP, and the test with it.
- **`wrangler.jsonc`'s `routes` is the Worker's whole set of addresses.** A route is declared there, never in Cloudflare's dashboard. Each deploy sends the list; depending on the key's rights, wrangler either replaces the Worker's routes with it or only adds to them and warns about the rest, so a route added by hand may survive a deploy unseen.
- **The Cloudflare key, the bot check's secret, the owner's email address and the evaluation key live only in the GitHub environment `production`,** which only `main` may use. The `check` job holds none of them. The `deploy` job installs nothing but the wrangler pinned in `deploy/`, refuses to run with any of the three Worker secrets empty, and hands them to wrangler in an owner-only file it deletes. The key can deploy Workers and their routes, read zones and edit the account's D1 databases, and nothing in DNS (`infrastructure/vendors/cloudflare/README.md`). Local runs use Cloudflare's public test keys (`npm run dev`), so no secret is ever on disk.
- **Never touch the zone's TXT records `_atproto` and `_dmarc`.** `_atproto` is what makes `whysosuresh.com` a Bluesky handle, and `_dmarc` is the mail policy. Their files under `infrastructure/` say so, and nothing in the site or the workflows can edit DNS.
- **Nothing private in any file:** no notes from outside this repository, no task or plan names, and no one's name but Suresh's.
