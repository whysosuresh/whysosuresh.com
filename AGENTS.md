# Agent guide: whysosuresh.com

This repository is whysosuresh.com, Suresh's home page: the static folder `site/`, served by one Cloudflare Worker, `whysosuresh-com` (`wrangler.jsonc`), which the `deploy` job in `.github/workflows/site.yaml` deploys on every merge to `main`. The Worker runs code only for `/api/*` (`src/`): the talk flow's send, which stores a recording in the database and the recordings' bucket after a bot check and two daily limits. Every page still comes straight from `site/`. Everything else it runs on (the zone, its records, the www redirect, the zone's settings, the database, the bucket and the bot check) is declared under `infrastructure/` and applied by Planton; read [`infrastructure/AGENTS.md`](infrastructure/AGENTS.md) before touching any of it. These are the laws for any change here.

## Laws

- **Run `npm run check` before every push.** It runs the three strict type checks (the tests, the site's scripts, the Worker, and that `worker-configuration.d.ts` matches `wrangler.jsonc`), wrangler's dry run, the site tests (`test/site.test.ts`) and the Worker tests (`test/talk.test.ts`), which run the dry run's bundle in workerd. Local commands run on the Node in `.nvmrc`.
- **Code style.** Strict TypeScript with no `any`; the site's scripts are plain JavaScript under `// @ts-check`. Every file opens with a comment that says what it is for. `worker-configuration.d.ts` is generated (`npm run types`), never edited by hand.
- **The Worker has no runtime dependencies.** Everything it needs is in the runtime and its bindings, so the deploy installs nothing but wrangler. It answers only JSON, with `Cache-Control: no-store`.
- **Nothing personal in a log line:** no name, email, address or token. A refusal logs its status and reason only. Cloudflare's automatic request records stay off (`invocation_logs: false` in `wrangler.jsonc`), because nothing says they leave out the visitor's address. No table keeps an address either; the limits count a salted hash that lives one day.
- **Migrations are numbered, only add, and are applied before the code.** `migrations/NNNN_name.sql`; the deploy applies them, then deploys. A migration never drops or renames what the running code reads, so a failed deploy leaves a working site. A new column arrives in the migration beside the code that first writes it.
- **The talk flow stays unlinked until its inbox ships.** No element opens it (`data-talk`); only `/#talk` does, and the test holds that. The button arrives with the inbox, so nobody talks into a box no one reads.
- **`site/` is an allowlist.** Every file it holds is served, and the list in `test/site.test.ts` names each one. A new file is added there on purpose, never by accident.
- **Links are clean and root-absolute:** `/` and `/feedback`, never `feedback.html` or `index.html`. The Worker redirects those with a 307, and a relative link breaks on the 404 page, which is served at any path.
- **Never `no-referrer`,** on a page, an element or a header. The YouTube player refuses to play without a referrer.
- **`site/_headers` matches the pages.** The test holds the expected set. A new kind of resource changes the CSP, and the test with it.
- **`wrangler.jsonc`'s `routes` is the Worker's whole set of addresses.** A route is declared there, never in Cloudflare's dashboard. Each deploy sends the list; depending on the key's rights, wrangler either replaces the Worker's routes with it or only adds to them and warns about the rest, so a route added by hand may survive a deploy unseen.
- **The Cloudflare key and the bot check's secret live only in the GitHub environment `production`,** which only `main` may use. The `check` job holds neither. The `deploy` job installs nothing but the wrangler pinned in `deploy/`, and hands the secret to wrangler in an owner-only file it deletes. The key can deploy Workers and their routes, read zones and edit the account's D1 databases, and nothing in DNS (`infrastructure/vendors/cloudflare/README.md`). Local runs use Cloudflare's public test keys (`npm run dev`), so no secret is ever on disk.
- **Never touch the zone's TXT records `_atproto` and `_dmarc`.** `_atproto` is what makes `whysosuresh.com` a Bluesky handle, and `_dmarc` is the mail policy. Their files under `infrastructure/` say so, and nothing in the site or the workflows can edit DNS.
- **Nothing private in any file:** no notes from outside this repository, no task or plan names, and no one's name but Suresh's.
