# Agent guide: whysosuresh.com

This repository is whysosuresh.com, Suresh's home page: the static folder `site/`, served by one Cloudflare Worker, `whysosuresh-com` (`wrangler.jsonc`), which the `deploy` job in `.github/workflows/site.yaml` deploys on every merge to `main`. The Worker runs code only for `/api/*` and `/threads/*` (`src/`): the note flow's send, which keeps a typed note as a new thread after a bot check and two daily limits, the threads' private calls under `/threads/api/`, behind their Cloudflare Access application, and the threads page (`src/pages.ts`), which it hands over from `site/threads/index.html` through the assets binding at `/threads/` and at every thread's own address, because no file can sit at every number. Everything Suresh keeps is a numbered thread with a history, kept by one store (`src/store.ts`). Every other page comes straight from `site/`, and `/inbox`, the threads' old address, redirects to `/threads/` (`site/_redirects`). Everything else it runs on (the zone, its records, the www redirect, the zone's settings, the database, the pages bucket, the bot check and Access) is declared under `infrastructure/` and applied by Planton; read [`infrastructure/AGENTS.md`](infrastructure/AGENTS.md) before touching any of it. These are the laws for any change here.

## Laws

- **Run `npm run check` before every push.** It runs the three strict type checks (the tests and `tools/`, the site's scripts, the Worker, and that `worker-configuration.d.ts` matches `wrangler.jsonc`), wrangler's dry run, the site tests (`test/site.test.ts`, `test/markdown.test.ts`, `test/keys.test.ts`), the command line's tests (`test/inbox-cli.test.ts`) and the Worker tests (`test/talk.test.ts`, `test/threads.test.ts`, `test/threads-door.test.ts`, `test/pages.test.ts`, `test/routing.test.ts`, `test/migrations.test.ts`), which run the dry run's bundle in workerd, in front of `site/` with the routing `wrangler.jsonc` declares. Local commands run on the Node in `.nvmrc`. `npm run dev:signed-in` serves the same bundle at `http://localhost:8790/` with made-up threads and Access played as the owner (`test/dev-signed-in.ts`; `--signed-out` for a visitor), which is how the threads page is looked at in a browser before a deploy.
- **Code style.** Strict TypeScript with no `any`; the site's scripts are plain JavaScript under `// @ts-check`. `tools/` is TypeScript that Node runs as is, so it uses only syntax Node can strip (no `enum`, `namespace` or parameter properties) and no dependency. Every file opens with a comment that says what it is for. `worker-configuration.d.ts` is generated (`npm run types`), never edited by hand.
- **The Worker has no runtime dependencies.** Everything it needs is in the runtime and its bindings, so the deploy installs nothing but wrangler. It answers only JSON, with `Cache-Control: no-store`, with one exception: a page saved into a thread (`src/page.ts`), the stored HTML its frame loads, which is answered with its own sealing CSP and `Cache-Control: private, no-cache` revalidated by its ETag.
- **Nothing personal in a log line:** no name, email, address or token. A refusal logs its status and reason only. Cloudflare's automatic request records stay off (`invocation_logs: false` in `wrangler.jsonc`), because nothing says they leave out the visitor's address. No table keeps an address either; the limits count a salted hash that lives one day.
- **Migrations are numbered and applied before the code.** `migrations/NNNN_name.sql`; the deploy applies them, then deploys. A migration adds, or drops only what no deployed code reads, in a deploy after the one that stopped reading it, so a failed deploy leaves a working site. It never renames. A new column arrives in the migration beside the code that first writes it.
- **The private door admits two callers: the owner's email and the sync's service token, checked by the Worker on every request.** Access guards `/threads/api` at the edge, one application with two policies, and `src/access.ts` checks Access's signature, issuer, audience and times again on every call under `/threads/api/`, against that application's tag (`THREADS_ACCESS_AUD`), so a token signed for any other application never opens it, then admits only the owner's address (`INBOX_OWNER_EMAIL`) or the sync's client id (`INBOX_SYNC_CLIENT_ID`). Access never guards a thread's own page, only its calls. A new caller is a new Access policy and a new check here, in one PR. The owner's page reads, starts threads of his own, makes the moves, comments and rewrites a thread's title, living summary or main text, every write only from his own page (`src/request.ts`). The sync reads, adds items (each once, by the origin it names), makes the page's moves, comments and rewrites a thread's title, living summary or the main text of a thread it wrote, without the page's same-origin check, which guards only a signed-in browser; marking the owner's mail opened stays his, and filing an item as an issue is the sync's alone. A visitor's own words are never rewritten. Nothing it adds or moves happens without the owner's word in the sync; that rule is the sync's, and the Worker's part is to refuse what isn't one of these.
- **The owner's email address is in no file.** The repository is public. Access reads it from a Planton secret, the Worker from the GitHub environment `production`, and the threads page from his sign-in; the site test fails on any address in the repository's files.
- **The "Send a note" doors open the note flow.** The home page and the Talk to me page each carry one (`data-talk`, first among their doors), and `/#talk` and `/#talk/<topic>` open it too; the test holds both. The doors arrived only once the inbox (now the threads) was live and proven, so nobody writes into a box no one reads: a change that takes the threads away takes the doors with it.
- **One topic list.** `site/talk-topics.js` is the topics a note can be about, read by the page and imported by the Worker. It stays plain data and pure functions, with no page and no side effect; the Worker's type check (no browser library) and the site test hold that. `site/spaces.js`, what a thread can be about, follows the same rules and holds every topic; the site test holds that too.
- **`site/` is an allowlist.** Every file it holds is served, and the list in `test/site.test.ts` names each one. A new file is added there on purpose, never by accident.
- **Links are clean and root-absolute:** `/` and `/feedback`, never `feedback.html` or `index.html`. The Worker redirects those with a 307, and a relative link breaks on the 404 page, which is served at any path.
- **Never `no-referrer`,** on a page, an element or a header. The YouTube player refuses to play without a referrer.
- **A page saved into a thread runs sealed, never on the site's own terms.** It is a Claude artifact's own HTML, so it is served only at its thread's call address with the headers `src/page.ts` sets (a CSP `sandbox` without `allow-same-origin`, claude.ai's page contract as its sources and no wider, `connect-src 'none'`), and framed by the threads page with the same sandbox tokens. The site's own CSP gains only `frame-src 'self'` for it; every library and font host lives in the frame's CSP alone. A page is saved by the sync only, as a new version: the object in the private bucket first, then its row, the object deleted again when the row isn't kept; versions are never overwritten or deleted.
- **`site/_headers` matches the pages.** The test holds the expected set. A new kind of resource changes the CSP, and the test with it.
- **`wrangler.jsonc`'s `routes` is the Worker's whole set of addresses.** A route is declared there, never in Cloudflare's dashboard. Each deploy sends the list; depending on the key's rights, wrangler either replaces the Worker's routes with it or only adds to them and warns about the rest, so a route added by hand may survive a deploy unseen.
- **The Cloudflare key, the bot check's secret and the owner's email address live only in the GitHub environment `production`,** which only `main` may use. The `check` job holds none of them. The `deploy` job installs nothing but the wrangler pinned in `deploy/`, refuses to run with either Worker secret empty, and hands both to wrangler in an owner-only file it deletes. The key can deploy Workers and their routes, read zones and edit the account's D1 databases, and nothing in DNS (`infrastructure/vendors/cloudflare/README.md`). Local runs use Cloudflare's public test keys (`npm run dev`), so no secret is ever on disk.
- **Never touch the zone's TXT records `_atproto` and `_dmarc`.** `_atproto` is what makes `whysosuresh.com` a Bluesky handle, and `_dmarc` is the mail policy. Their files under `infrastructure/` say so, and nothing in the site or the workflows can edit DNS.
- **Nothing private in any file:** no notes from outside this repository, no task or plan names, and no one's name but Suresh's.
